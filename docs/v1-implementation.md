# V1 implementation

This document is the build spec for **v1 only**: the trip planner app and how it is deployed. Later phases (Kubernetes, API gateway, extra microservices, plan edits, live booking APIs) are out of scope here.

## Goal

A one-shot **chat** trip planner. The user describes a multi-city trip in natural language. The system returns either:

- a grounded itinerary (flights + hotels), itemized bill, and remaining budget, or
- a clear failure if no plan fits the budget and constraints.

Nothing is purchased. “Book” means **select** inventory from local datasets.

Typical trip size: **3–5 cities** (origin, intermediate stays, final destination which may differ from origin).

---

## What v1 does

The user sends one prompt, for example:

> Economy for 2 people. DEL → NYC 3 nights, NYC → Las Vegas 2 nights, Las Vegas → California 3 nights, then return to Hyderabad. 3-star hotels with gym and complementary breakfast. Budget $4000. Fine if we go $20 over.

The app must:

1. Turn that prompt into a **structured trip spec** (JSON).
2. Search **local** flight and hotel catalogs with **deterministic** filters.
3. Return only a **shortlist** per search (not the full catalog) to the planner.
4. Stitch a multi-city plan under budget, with timeline checks (flight times vs hotel check-in/out).
5. Ask the model only to **write up** a plan that already exists in code (or to phrase a structured failure).

If the prompt omits nights per city, v1 **fails validation** with a clear error. No clarifying chat loop.

---

## What v1 does not do

- Payments, PNR, real airline/hotel booking
- Multi-turn plan edits (“make Vegas one more night”)
- Asking the user how many days to stay
- Live GDS / hotel APIs (use CSV/JSON fixtures)
- Separate deployable `get_flights` / `get_hotels` processes, API gateway, Kubernetes
- Soft amenities (“gym if possible”) — amenities are **hard filters**

---

## Design rule

| Layer | Responsibility |
|---|---|
| Gemini | Parse the prompt into JSON; later, write the itinerary in English from a **finished** plan |
| Python | Filter, sort, shortlist, budget math, timeline legality, pick the winning plan |
| Datasets | All inventory and prices |

The model never scans thousands of rows. Search tools return on the order of **5** flights or hotels per query. The reporter model sees **one** chosen plan (or a small set of already-scored plans), never raw catalogs.

Gemini is accessed only through `app/llm.py` (`complete`, `complete_json`, optional tools). The rest of the app does not import the Google client.

**Default CLI** (`python -m app.main "..."`): extract `TripSpec` → `plan_trip` → reporter. Gemini does **not** pick inventory. `python -m app.main --tools "..."` is the older function-calling agent.

---

## Execution flow

```
User prompt
    → Extractor (Gemini) → TripSpec JSON  (`app/extract.py`)
    → Validate spec in code (`app/trip_spec.py`)
    → Planner: shortlists, timeline, budget  (`app/planner.py`)
    → Reporter (Gemini): itinerary + bill from that plan only  (`report.py`)
```

CLI: `python -m app.main "..."`. FastAPI `POST /chat` is later. No follow-up messages in v1.

---

## Trip spec (extractor output)

Pydantic models in `app/trip_spec.py`, validated after Gemini returns JSON (or built by hand in tests).

This is **not** a flight. `search_flights` is already the one-leg lookup. The trip spec is the **whole trip**:

- `legs[]`: only hops the user asked for. One object = one-way. A return exists **only** if a second (or last) leg is listed. Never infer a round trip.
- `stays[]`: `city`, `nights` (required), optional `check_in`
- `passengers`, `cabin`
- `hotel`: `min_stars`, `amenities[]` (hard filters)
- `flight`: optional copy of search filters (`time_of_day`, price range, `sort_by`, `is_refundable`) applied to every leg in v1
- `budget_cap`, `overage_allowed` (default `0`)

Extraction rules (prompt + schema, **enforced in code**):

- If the user says nothing about overage → `overage_allowed = 0` (hard cap).
- If they say “fine if $10–20 over” → `overage_allowed = 20` (use the top of the range).
- If they say “strictly within budget” → `overage_allowed = 0`.
- Amenities named in the prompt become required filters.

Feasible means:

`total_cost <= budget_cap + overage_allowed`

If no combination satisfies that, **fail clearly** (over by $X, expensive legs). Do not invent cheaper inventory.

**Budget slack:** if a valid plan costs less than the cap, leftover is `budget_cap - total` (or vs `budget_cap + overage_allowed` only for the legality check). V1 ranking: **cheapest valid itinerary** (largest leftover under the hard/soft cap).

## Data

Static catalogs in-repo (CSV or JSON):

**Flights** — generated by `scripts/generate_flights.py` into `data/flights.csv.gz` (and `data/airports.csv`).

Query store: **SQLite** at `data/catalog.sqlite` (tables `airports`, `flights`, `hotels`). Built by `scripts/build_flights_db.py`; hotels loaded with `scripts/build_hotels_db.py` (does not rebuild flights). Search tools query this DB, not the gzip CSV.

Catalog rules (v1):

- 50 well-known airports (IATA), all directed pairs, **calendar year 2026 only**
- **10 flights per origin→destination per day**, both `economy` and `business` (so HYD→MUC on a given date still has 10 options per cabin)
- Columns: `offer_id`, `flight_number`, `airline`, `origin_city`, `origin_airport`, `destination_city`, `destination_airport`, `depart_date`, `depart_time`, `arrive_date`, `arrive_time`, `duration_minutes`, `stops`, `cabin`, `price_usd` (per passenger), `seats_available`, `is_refundable` (`yes`/`no`)

Planner search keys: airports/cities, `depart_date`, `cabin`. Timeline uses `depart_time` / `arrive_date` / `arrive_time`. `seats_available` and `is_refundable` are inventory flags for later filters or the write-up; v1 planner may ignore them.

**Hotels** — generated by `scripts/generate_hotels.py` into `data/hotels.csv`, loaded into the same SQLite file by `scripts/build_hotels_db.py` (`hotels` table; does not rebuild flights).

Columns: `hotel_id`, `name`, `city`, `city_name`, `stars`, `cost_per_day` (per room), `rooms_available` (integer; search requires `>= 1` since v1 books one room), `amenities` (pipe-separated), `check_in` / `check_out` (15:00 / 11:00). About 12 hotels per city, including some **without** gym or breakfast so amenity filters can fail honestly. Stored in SQLite table `hotels` inside `data/catalog.sqlite` (same file as `flights` and `airports`; rebuild hotels only with `scripts/build_hotels_db.py`).

## Deterministic search

### Flights

Filter by origin, destination, date, cabin. Optional (only when the user specified them): `time_of_day` (morning 05:00–11:59, afternoon 12:00–16:59, night 17:00–04:59 local depart), `min_price_usd` / `max_price_usd`, `sort_by` `price` (default) or `duration` (`duration_minutes`, least travel time), `is_refundable` `yes` / `no`. Return **top 10**. Booking is not in v1 (add after hotels).

Price in the plan: `price * passengers`.

### Hotels

Filter by city, `stars >= min_stars`, **all** requested amenities present. Sort by `cost_per_day` ascending. Return **top 10**.

V1 party rule: **always 1 room**, even for 1 passenger. Cost: `cost_per_day * nights * 1`. A room is assumed to sleep two; we do not add a second room in v1.

## Planner

The planner is ordinary Python (no LLM).

1. Build ordered legs: origin → stay1 → stay2 → … → final destination.
2. For each leg and stay, use shortlists from search.
3. Enumerate combinations with a **bounded** search (3–5 cities, top 5 per slot is enough; prune as soon as partial cost exceeds cap).
4. Apply **timeline** rules; drop illegal pairs.
5. Sum costs; drop over `budget_cap + overage_allowed`.
6. Among survivors, pick minimum `total_cost`.
7. Emit a `Plan` object: flight ids, hotel ids, nights, line items, `total`, `remaining`.

### Timeline (v1)

- `N` nights in a city = `N` hotel nights. One hotel per night; never two hotels the same night.
- Incoming flight arrives on the **check-in date** of night 1 (same local date).
- Outgoing flight departs on the **checkout morning** after night `N`.
- Default hotel `check_in=15:00`, `check_out=11:00`.
- Outbound is illegal if `depart_time` is before `check_out` minus a **3 hour** airport buffer (v1 constant).
- Early inbound (before check-in) is **allowed**; the night is still charged; the write-up may mention waiting until check-in. Do not assume early check-in.
- No hotel on the origin night before first departure unless the spec says so (v1: it does not).
- No hotel after the final return flight.

Late-night arrivals still count as night 1 in that city.

## Reporter

Second Gemini call. Input is **only** the `Plan` JSON (or the structured failure). Output is the chat message: itinerary, breakdown, remaining money.

Guardrail: every `flight_id` / `hotel_id` in the text must exist on that plan. Prefer having the reporter copy ids from JSON rather than invent names. Evals should fail on unknown ids.

## HTTP API (`app/api.py`)

FastAPI app in `app/api.py`. CLI remains `python -m app.main`. Run:

```text
uv run uvicorn app.api:app --reload
```

Interactive docs: `http://127.0.0.1:8000/docs`.

The planner still calls flight/hotel **functions** in-process. HTTP is a face on top of `run_pipeline` / `plan_trip` / dummy booking.

| Method | Path | Role |
|---|---|---|
| `GET` | `/health` | Liveness |
| `POST` | `/chat` | Full pipeline (Gemini extract → `plan_trip` → report). Body: `{ "prompt": "..." }` |
| `POST` | `/plan` | `TripSpec` JSON → `plan_trip` (no Gemini). Useful for evals |
| `POST` | `/book_flights` | Dummy confirm: lookup `offer_id`, return a fake `booking_ref`. No payment |
| `POST` | `/book_hotels` | Dummy confirm: lookup `hotel_id`, reject if `rooms_available < 1`. No payment |

Pydantic request models in `app/api.py`: `ChatRequest`, `ChatResponse`, `BookFlightRequest`, `BookHotelRequest`. `/plan` reuses `TripSpec`.

Not in this file yet: `GET /flights`, `GET /hotels`, `GET /metrics`. Search stays on the Python catalog modules. Prometheus scrape can wait until Compose.

## UI

Static page in `frontend/` (Newsreader serif, warm Claude-like palette). Served by FastAPI at `GET /`; CSS/JS at `/assets`. The page `POST`s `/chat` and dummy-books `/book_flights` and `/book_hotels`. Ctrl/Cmd+Enter sends. Open `http://127.0.0.1:8000/` after `uv run uvicorn app.api:app --reload`.

## Evals and harness

Planner evals live in `tests/` and **do not call Gemini**. Run:

```text
uv run pytest
```

Current fixtures:

- Spec: one-way has no implied return; a return exists only as a second leg; 2 stays + 1 flight is invalid.
- Extract enrich: dropped stars/amenities/afternoon are filled from the prompt text.
- `plan_trip` vs `catalog.sqlite`: afternoon + gym/breakfast under budget; `$50` cap → `over_budget`; fake amenity → `no_hotels`; listed return HYD←MUC on checkout date; 07:00 vs 11:00 checkout → timeline reject.

Money checks: `total == sum(line_items)`. Ids must look like catalog `FLT-` / `HTL-`. Skip planner tests if the SQLite file is missing.

## Observability (instrument now, dashboards can be thin)

Every `/chat` gets a `request_id`.

**Prometheus (scrape `/metrics`):**

- process/app health (`up`, request latency, error rate)
- `gemini_calls_total` (labels: `stage=extract|report`)
- `tool_calls_total` (labels: `tool=flights|hotels`)
- `plans_total` (labels: `result=success|infeasible|invalid_spec`)
- `plan_total_cost` / leftover as histograms or summaries if useful

**Logs:** structured JSON with `request_id`, spec summary, shortlist sizes, chosen ids, Gemini latency.

**Traces:** OpenTelemetry spans for extract, each search, plan, report. V1 can export to console or an OTLP sidecar; Grafana/Tempo can wait until Compose is stable. Do **not** confuse per-call traces with Prometheus counters — both are required for the story, counters first.

## Deployment (v1): Docker Compose

**Priority is Docker.** One (or two) containers you can run locally and on a single VM.

### Images

- `app`: FastAPI (uvicorn), serves API + static UI or a second tiny `web` service if the frontend is built separately.
- `prometheus`: scrape `app:8000/metrics`.
- `grafana` (optional in the same Compose file): provision a datasource to Prometheus; empty/minimal dashboards are fine.

No API gateway. Services talk on the Compose network (`http://app:8000`).

### App container

- `GET /health` for Compose healthcheck.
- Read catalogs from an image path or a mounted `./data`.
- Environment: `GEMINI_API_KEY`, log level, optional OTLP endpoint.

### Compose outline

```text
services:
  app:        # FastAPI
  prometheus: # scrape app
  grafana:    # optional, Prometheus datasource
```

Bring-up: `docker compose up --build`. Catalog is mounted from `./data` (not baked into the image). UI: `http://127.0.0.1:8000/`.

### What “deployed” means for v1

- Reproducible `docker compose up` on a clean machine.
- Health endpoint green.
- Prometheus showing `up` and Gemini/tool counters after a `/chat`.
- API key not in git.

### Explicitly later (not v1 deploy)

- Kubernetes, cluster health dashboards, Helm
- Ingress / API gateway
- Splitting flights, hotels, planner into separate Deployments

When that happens, **reuse the same app image** and `/metrics` / `/health`. V1 instrumentation should not assume a cluster.
